这篇文章写给刚开始用 coding agent 做项目的实习生和初级工程师。你可能在 Slack、飞书或 issue 里接到一个需求，再让 Codex 帮你读代码、改文件、跑测试，最后准备 Git 提交。代码很快就有了，真正让人犯难的常常是：我怎么知道它做对了？

一次改动可能有几百行，散落在好几个目录里。逐行读完要花不少时间，也不一定能看出需求从一开始就理解错了。代码看起来整齐，测试也通过了，功能却可能和用户想要的不是一回事。

所以 review 不能只留到最后。它从接到需求时就开始了。一个人要逐渐学会看清目标、理解方案，再判断代码有没有兑现这两件事。读 diff 很重要，但它只是这段工作的一个部分。

## 人参与 review，不只是最后点一下批准

Human in the loop 常被理解成“AI 写完，人来审批”。人需要在需求、方案和验证几个关口作判断：把模糊请求变成可验收的行为，确认方案符合系统约束，再依据证据决定是否合并。Agent 可以写代码、查资料、跑命令；需求取舍、上线风险和后续维护仍由团队负责。

这也是人和 agent 在 review 中能发挥不同作用的地方。2026 年一项预印本研究分析了 300 个 GitHub 开源项目、27 万多段 review 对话：agent 评论多在找缺陷和改善代码；人还会追问设计意图、检查测试、传递项目知识。进入最终代码的 agent 建议占 16.6%，人类建议占 56.5%。这不是准确率比较，却提醒我们不要把 agent 的发现直接当作待办清单。研究者抽样查看未采纳的 agent 建议，其中 28.7% 被判为错误，24% 虽然发现了问题，提出的却是与作者最终选择不同的修法。数据来自成熟开源项目，而且是观察既有 review，不能证明人总是更准；它显示的是一种分工：agent 扩大筛查面，人负责理解上下文、追问意图和决定取舍。[研究：Human-AI Synergy in Agentic Code Review](https://arxiv.org/abs/2603.15911)

因此，人参与不等于自己从头重写或逐行复读 agent 的工作。你要把判断放在关键位置：先核对目标和方案，再决定哪些风险必须人工确认。Agent 可以帮忙梳理调用关系、找可能的边界输入；你要追问它依据的是哪段代码、哪条测试，之后自己核实。没有证据的自信说明，不能替代理解。

## 资深工程师先看方向，再看实现

Google 的公开 reviewer 指南把设计列为 review 最重要的部分：功能是否应该进入这个系统，和周围模块能否配合，是否满足代码的使用者。这里的使用者不只是产品用户，也包括以后要调用、维护这段代码的工程师。资深 reviewer 会先弄清这次改动要兑现什么，再决定实现细节是否合理。[Google：What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

比如需求只写着“失败后自动重试”，还没有说明哪些错误可以重试、最多几次、会不会重复扣款或发送消息。此时直接逐行检查 agent 写出的循环，可能只是把错误方案审得更仔细。先把这些问题问清楚，补上验收条件和不变量，再让实现继续，能省下很多无用的 review 时间。改动范围大时，也可以先让 agent 列出方案、触及的模块和待确认假设，再把实现切成几段，每段对应一个可验证的行为。

方向明确后，资深 reviewer 会追问改动对系统的影响：接口和旧数据是否兼容？失败时状态会不会卡住？并发请求会不会重复操作？监控和回滚能否收住问题？Google 指南要求 reviewer 理解受审改动的每一行，并结合整个文件和系统上下文判断。风险排序是为了把注意力放对地方，不是给没读懂的代码盖章。看不明白就请作者解释或拆小；涉及隐私、安全、并发、迁移等专门知识时，找合适的维护者补审。

AI 加快生成，也可能把更大的改动批量送到 review 阶段。DORA 2025 的模型估计，AI 采用率提高 25% 与交付吞吐下降 1.5%、稳定性下降 7.2% 相关；报告把更大的变更批次列为可能原因之一。这个组织层面的关联不能证明 AI 直接导致了退化，却提醒我们控制每次交付的范围：一个提交解决一个清楚的问题，审查者才容易判断方向、影响和回滚办法。[DORA：State of AI-assisted Software Development 2025](https://dora.dev/ai/gen-ai-report/report/)

## 好的 review 会解释理由，也会教人判断

资深工程师也不会把所有建议都当成必须修改的命令。Google 的标准是：改动明确改善了整体代码健康，就不必为了追求完美而卡住提交。重要问题要讲清影响和依据；风格偏好可以作为非阻塞建议。reviewer 对代码健康负责，也要让作者继续推进工作。[Google：The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)

解释为什么，比只给替换写法更能帮初级工程师成长。2025 年一项 ACM 研究分析了 793 条 review 评论，发现 42% 只有建议，没有解释。研究者归纳了说明规则、引用类似案例、解释未来影响等方式。比如，与其只写“改成事务”，不如说明：“如果写入成功、事件发送失败，两个系统会对不上；这里需要事务或失败补偿。”作者听懂理由，下次才可能认出同一类问题。[研究：Explaining Explanations](https://doi.org/10.1145/3708518)

review 也不是找一位全知的人包办所有判断。好的 reviewer 会说明自己看了哪一部分、哪里还不确定，并为隐私、安全、性能或并发问题找对应的维护者。初级工程师也可以这样做：负责核对需求、追踪调用链和检查测试；遇到解释不清的业务约束，就请熟悉它的人补足背景。

## 怎样把每次 review 变成自己的练习？

读代码前，写下需求要改变的行为、涉及的模块和最担心的失败。再沿关键路径从输入追到结果，核对测试能否在实现错误时失败。Google 也提醒，测试本身要审：断言有没有意义，错误实现会不会照样通过？UI 变化走一遍用户路径；并发代码推演状态和时序。

接着再请 agent 做第二视角。你安装的 `mattpocock-skills:code-review` 能把“是否符合需求”和“是否符合仓库规范”分开检查。给它明确的比较基点和 issue 或规格，先自己做判断，再对照它提出的盲点。Agent 的发现不等于结论：回到源代码、测试和项目约定确认，尤其要小心它不熟悉的历史决策。

Anthropic 在 2026 年公布的一项随机研究也提醒我们留出思考空间。52 名、以初级工程师为主的参与者学习 Python 异步库后，AI 辅助组的即时测验平均为 50 分，手写组为 67 分；完成任务的时间差异没有达到统计显著。研究只测即时理解，实验助手也不同于真实 coding agent，不能据此断言工作中的 AI 会让人退步。掌握较好的参与者会追问概念、要求解释，并在自己写代码时用 AI 检查理解。用 AI 学习与把任务直接交给 AI，是不同的参与方式。[Anthropic：How AI Assistance Impacts the Formation of Coding Skills](https://www.anthropic.com/research/AI-assistance-coding-skills)

每次 review 结束后，记下一条你刚学会的项目约束，或一个自己漏看的失败路径。遇到真实 bug，可以用 `mattpocock-skills:diagnosing-bugs` 先复现并缩小原因，再用 `mattpocock-skills:tdd` 把失败场景固定成回归测试。若你看不清模块为什么这样划分，`mattpocock-skills:codebase-design` 可以帮你整理接口和职责。技能负责提供练习结构，判断仍要落回你对项目和证据的理解。

## 项目要掌握到什么程度？

初级工程师不必先读完整个仓库。对当前改动，至少要能讲清需求对应的可见行为、涉及的模块和接口、重要数据怎样流动、哪些不变量不能破坏，以及测试和回滚入口在哪里。碰到高风险或超出自己经验的路径，就请模块维护者一起看。掌握项目不是记住所有文件，而是知道改动会碰到谁、证据在哪里、自己还缺哪块背景。

如果你能在 review 前形成自己的判断，review 后又能用代码和测试解释它，AI 就是在放大你的能力。若只留下更多代码和一条“测试通过”，却没人理解改了什么、为什么能工作，那就是 AI slop 开始堆积的信号。

## 总结

Review agent 写的代码，先要判断目标和方案，再按风险核验实现与证据。人参与的价值在于理解项目上下文、追问意图、承担影响判断，也把理由传给下一个维护者。每次 review 都让自己多懂一点系统，才会越用 AI 越强。
