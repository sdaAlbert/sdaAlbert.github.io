上一篇文章已经讨论过 Agent 为什么需要持久状态、如何面对结果不明的工具调用，以及恢复时为什么不能只相信 Context。

这一篇我想把视角往后端再推进一步：一项 Agent 任务进入系统后，会产生哪些完全不同的数据流？它们分别要求怎样的吞吐、延迟、事务和保留能力？只有回答这些问题，RDS、Redis、Kafka 或工作流系统才有明确的位置。

这也意味着，文章不会给出一套“Agent 标准技术栈”。成熟产品公开出来的设计恰恰说明，它们优先固定的是 session、执行环境、事件和权限之间的接口，底层存储反而可以替换。

## 1. 一项任务进入后端后，实际上分成了六条流

从用户提交任务开始，后端并不是简单地把一条消息扔给 Worker。

```text
用户请求
  ↓
创建 Run ──────────────── 状态流
  ↓
产生待执行步骤 ─────────── 调度流
  ↓
分配 Worker 与执行环境 ─── 资源流
  ↓
模型和工具持续返回结果 ─── 事件流
  ↓
保存文件、网页、代码产物 ── 产物流
  ↓
向 UI、审计和评测提供数据 ─ 投影与观测流
```

状态流回答“任务现在怎样了”。例如正在运行、等待审批或已经完成。

调度流回答“下一步交给谁做”。它负责排队、限流、领取和重试。

资源流回答“在哪里做”。它管理 Worker、容器、浏览器和 Sandbox 的创建与回收。Worker 就是后台真正执行任务的进程；Sandbox 则是与主系统隔离的临时执行环境。

事件流回答“刚才发生了什么”。例如工具调用完成、审批到达或 Run 状态改变。

产物流保存执行留下的大文件。例如代码补丁、网页快照、音视频和生成文件。

投影与观测流把过程展示给人。用户在这里看进度，工程师在这里查日志、指标和 Trace。Trace 可以理解为一次请求经过各个服务时留下的行程记录。

这六条流小规模时完全可以共用少量组件。随着系统变大，后文会按一条主线展开：

- 第 3 节先处理状态流：把任务的“账”记清楚；
- 第 4 节再拆调度流：让大量 Worker 不必争抢数据库；
- 第 5 节扩展事件流与投影流：让多个下游都能看到同一批事件；
- 第 6 节处理资源流：让长任务可以释放 Worker，也能管理 Sandbox；
- 产物流和观测流贯穿四个阶段。文件一大就移出主库，排障数据一多就进入专门系统。

所以，技术选型都应能回答一个问题：它究竟在服务哪一条流？如果回答不出来，这个组件很可能还不需要引入。

## 2. 先看两个企业系统怎样拆这些流

先只看两个例子。字节的公开项目更适合观察“不同数据放在哪里”，腾讯的公开实践更适合观察“通信和执行怎样分开”。

### 字节：结构化数据、分析数据和异步任务分开承载

Coze Loop 没有把所有数据都塞进一个数据库。

- MySQL 保存用户、权限和评测任务。它是关系数据库，适合保存结构清楚、需要事务的数据。
- ClickHouse 保存大量 Trace 和评测明细。它更像分析仓库，擅长快速扫描海量记录，但不适合处理每笔业务事务。[Coze Loop Architecture](https://github.com/coze-dev/coze-loop/blob/main/ARCHITECTURE.md)

此外，Redis 用来放缓存和短期数据。它读写很快，但不应默认成为所有业务事实的唯一存档。MinIO 是对象存储，用来放文件。RocketMQ 是消息队列，用来通知后台服务异步做事。

把它放回六条流就很清楚了：MySQL 承担状态流，RocketMQ 承担调度流，ClickHouse 承担观测分析，MinIO 承担产物流。Redis 只是加速其中一些短期访问。

这并不意味着小团队一开始也要部署五个组件。真正值得借鉴的是拆分顺序：先用关系数据库把业务跑通；文件变多后移到对象存储；分析查询拖慢主库后再加分析系统；后台任务需要独立扩容后再加队列。

### 腾讯：通信常驻，但昂贵的执行资源按任务启停

腾讯云公开的 Agent Runtime 关注另一个问题：用户连接需要一直在线，但代码或浏览器环境只在执行时才需要。如果把两者绑在一起，为了维持连接，昂贵的执行环境也要一直开着。

它把通信交给常驻网关，再通过消息队列唤醒 Sandbox。Sandbox 可以按任务创建、暂停和恢复。[腾讯云 Agent Runtime 实践](https://developer.cloud.tencent.com/article/2686331) 腾讯开源的 CubeSandbox 进一步使用轻量虚拟机隔离不可信代码，并用快照降低再次启动的时间。[CubeSandbox Architecture](https://github.com/TencentCloud/CubeSandbox/blob/master/docs/architecture/overview.md)

这里，消息队列服务调度流，Sandbox 服务资源流。Redis 只记录资源协调信息，例如哪个 Sandbox 正在被使用，它不等于 Agent 的业务数据库。

两个案例放在一起看：字节按数据的用途拆存储，腾讯按计算资源的生命周期拆执行。它们都不是先列一份技术清单，而是先找到哪条流已经出现了独立压力。

## 3. 情况一：任务还不多，先把账记清楚

这一阶段首先解决状态流。目标很简单：无论 Worker 是否还活着，系统都能回答任务现在进行到哪里。

先做一个粗算。

假设系统每天运行 10 万个 Run。每个 Run 平均改 10 次状态。一天就是 100 万次写入，平均约 12 次每秒。即使高峰是平均值的 10 倍，也只是约 120 次每秒。

这只是估算，不是数据库的性能承诺。它想说明一件事：先算数量级，再谈架构。System Design 常用的算法也很朴素：日请求量除以 86,400 得到平均每秒请求，再单独估高峰、数据大小和保留时间。[System Design Space 的估算说明](https://system-design.space/en/chapter/back-of-envelope-estimation/)

在这个阶段，PostgreSQL 或 MySQL 往往已经够用。它们都属于关系数据库：数据按表保存，可以用事务保证几项修改要么一起成功，要么一起失败。可以把它想成一本账。Run 当前走到哪一步，谁批准了什么，花了多少预算，都记在这里。

RDS 也常在架构图中出现，它是云厂商帮你托管 PostgreSQL、MySQL 等数据库的服务。备份、故障切换和升级由平台承担一部分。

任务不多时，Worker 可以直接从数据库领取待办。创建 Run 时，再在同一个事务里写一条“等待派发”的记录。这条记录通常叫 Outbox。它像夹在账本里的发货单，可以避免“账已经记了，任务却没有发出去”。[AWS Transactional Outbox](https://docs.aws.amazon.com/en_en/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

什么时候该升级？看症状，不看口号：

- Worker 为了抢任务，不停查询数据库；
- 领取任务的锁开始拖慢产品查询；
- 重试、优先级和延迟执行让 SQL 越来越绕；
- 增加 Worker，吞吐却不再增加。

这些问题没有出现，就先别加新组件。

### 这一阶段虽然刚开始，但也要照顾另外两条流

大文件进入对象存储。对象存储可以理解为专门放文件的云端仓库，数据库只保存文件地址。

网页快照、音视频片段、代码补丁、模型输入和工具输出可能远大于一条状态记录。它们还可能有不同的生命周期和访问权限。这类内容适合进入对象存储，Run 中只保留引用、哈希、版本和权限信息。恢复时取回同一份输入，既避免数据库膨胀，也能证明这次模型判断基于哪个版本的材料。

日志和 Trace 进入观测系统。SSE、WebSocket 和轮询展示的是 Run 的投影，不应成为事实本身。连接断开后，前端应该能从持久状态重新构造进度。

同样，日志也不能只按容器查看。一次执行至少要串起 `run_id`、`step_id`、`tool_call_id`、`effect_id`、`provider_request_id` 和 `trace_id`。否则系统只能知道某个服务报过错，却无法解释用户这次任务究竟停在哪里。

这一节的判断：状态流没有明显压力时，继续使用关系数据库；先把状态、索引和事务边界做好，不要提前引入更多存储。

## 4. 情况二：Worker 变多，需要一个“取号机”

这一阶段要把调度流从状态流中拆出来。数据库继续记账，队列开始负责派活。

数据库轮询在小规模时很方便。轮询就是 Worker 定时去问数据库：“有我的活吗？”Worker 多了，就像一群人不断跑到前台问同一句话。假设 100 个 Worker 每秒查一次。即使没有任务，数据库也要处理 100 次查询。扩到 1,000 个 Worker，就是每秒 1,000 次空问。

这时可以加入消息队列。它像取号机：任务到了再叫人，Worker 不必围着数据库转。队列还会记录任务是否被领取、多久没有完成、是否需要再次派发。

引入下面哪一种，取决于已有环境：

- Redis 的优势是延迟低，也方便保存短期 lease、heartbeat 和限流计数。Redis Streams 是其中专门保存消息序列的功能。它能把消息分给一组 Worker，也会记录哪些消息已经领取但尚未完成。系统本来就在使用 Redis、任务量还没有大到需要独立消息平台时，它通常比较顺手。它适合作为协调层，却没有必要成为 Run 的唯一事实来源。[Redis Streams](https://redis.io/docs/latest/develop/use-cases/streaming/)
- SQS 是 AWS 托管的消息队列。团队不必自己维护服务器，可用性和扩容主要交给云厂商。代价是更依赖云平台。
- RabbitMQ 是专门的消息服务。它适合需要多种路由、优先级和复杂投递规则的系统，但也需要团队自己理解和维护它。

不管选谁，边界都不要变：数据库保存任务状态，队列只负责叫醒 Worker。队列里尽量只放任务编号和少量派发信息。为了避免两个 Worker 同时写入，也可以在 Run 上维护 `owner`、`lease_until`、`version` 或 fencing token。

投递仍可能重复。因此 Worker 要能认出：“这一步我已经做过了。”这比假设消息永远只来一次更可靠。

这一节的判断：调度流出现大量空轮询、领取锁或积压时，再引入队列。

## 5. 情况三：一份事件要送给很多下游

这一阶段扩展的是事件流和投影流。同一件已经发生的事，需要同时告诉通知、计费、审计、评测和前端。

普通任务队列更像出租车。一条任务通常只交给一个 Worker。事件流更像报社：同一份报纸可以送到很多订户手里，新订户还可以翻阅保存下来的旧报纸。

再做一个粗算。假设每秒产生 100 条事件，每条 1 KB。原始数据一天约 8.6 GB。如果有 5 个下游，系统每天要完成约 4,320 万次消费。保留 30 天，原始事件约 259 GB。副本和索引还没有算进去。

当 `ToolCommitted` 不只用于推进 Agent，还要同时进入审计、评测、通知、计费和数据分析，普通任务队列会开始吃力。下游可能希望按自己的节奏消费，甚至从三天前重新计算一次指标。

Kafka 就是为这类场景设计的分布式事件日志。不同 consumer group 可以独立维护消费进度，因此适合多订阅方、历史重放和数据管道。

只有一个执行集群和一个结果处理器时，普通队列已经够用。出现下面的需求后，Kafka 才开始有价值：

- 多个下游需要各读一遍，而不是互相抢消息；
- 新服务上线后，要重放过去的数据；
- 事件需要保留数天或数月；
- 单机或单队列的吞吐已经不够。

[Kafka 的设计](https://kafka.apache.org/design/)把同一类事件放进一个 Topic。Topic 可以理解为一个栏目。每类下游各自组成 Consumer Group，也就是一组读者。通知系统读到哪里，不会影响审计系统的进度。数据量变大后，一个 Topic 还可以切成多个分区并行处理。

Kafka 不负责回答“这个 Run 现在完成了吗”。这个答案仍应放在业务数据库，或者由事件整理出的查询页面背后。Kafka 保存的是发生过的事。数据库保存的是现在的结果。

所以不要先问“要不要上 Kafka”。先问：同一份事件，到底有几类读者？它们要不要回看历史？

这一节的判断：事件流只有一个消费者时，普通队列通常够用；出现多个独立消费者、长期保留或历史重放需求时，再考虑 Kafka。

## 6. 情况四：任务很长，Worker 不能一直守着

这一阶段主要处理资源流，同时也会反过来影响状态流和调度流。任务离开当前 Worker 后，系统仍要记得它在等什么。

有些任务并不频繁，却会等待很久。它可能等人工审批，等明天的定时器，等外部系统回复，也可能等几个子任务都完成。

假设有 1 万个任务要等待 24 小时。让 1 万个 Worker 一直睡在那里，像让 1 万名快递员站在门口等客户签收。计算资源被占住了，进程重启后还可能忘记自己在等什么。

更合适的做法是“存档，再设闹钟”：

1. 把当前步骤和等待条件持久化；
2. 释放 Worker；
3. 审批、回调或定时器到来后，再领取下一步。

如果只是少量等待，用数据库记录状态，再定时寻找到期任务就够了。如果任务经常等待数小时，还要同时启动几项工作、等它们会合，或者失败后执行善后步骤，才值得加入专门的工作流系统。

工作流系统不是“更快的队列”。它更像流程管理员。它记住任务走到哪一步、正在等待什么，以及信号到来后该继续哪一步。

Sandbox 是另一件事。它是执行代码、浏览网页或操作桌面时使用的隔离工作间。需要时再创建，暂时不用时可以暂停、保存快照或回收。长期状态放在数据库、Git 或对象存储，不要只留在这个临时工作间里。

工作流层像存档和闹钟。Sandbox 像临时工作间。两者解决的都不是“消息发得够不够快”，而是任务离开当前进程后，系统还能不能继续往下走。

这一节的判断：资源流只需要短暂执行时，Worker 加容器就够了；一旦任务要跨小时等待，或执行环境需要隔离、暂停和回收，再引入工作流和 Sandbox Controller。

## 7. 开始搭建之前，先把这些问题想清楚

Agent 基础架构不需要从一张塞满中间件的图开始。回到开头的六条流，可以把全文压缩成一条判断顺序：

```text
先画出六条流
→ 找到真正出现压力的那一条
→ 只为它增加新的基础设施
```

把上面这条主线放进一个小例子：一开始假设系统每天处理 1 万个 Run。

```text
关系数据库记录状态
→ Outbox 记录待派发任务
→ Worker 从数据库领取并执行
→ 文件进入对象存储
→ 日志和 Trace 进入观测系统
```

当 Worker 变多，数据库开始被大量空轮询拖慢，就把“叫醒 Worker”这件事交给 Redis Streams 或云消息队列。数据库继续保存 Run 的真实状态。

当评测、审计、计费都要独立读取同一批事件，并且希望回看历史，再把事件写入 Kafka。Kafka 保存发生过的事，数据库仍保存 Run 当前的结果。

当任务需要等待人工审批、外部回调或隔夜定时器，再加入工作流层；当任务需要执行代码或浏览网页，再加入 Sandbox Controller 管理临时环境。

每一步都对应前文的一条数据流，也都应该由实际压力触发。

真正可靠的 Agent 基础架构，并不是每一层都使用最复杂的产品，而是每一种数据都有明确归属，每一个组件都有可解释的引入条件，并且某个 Worker、连接或 Sandbox 消失后，系统仍然知道下一步应该由谁负责。
